# 디버깅

> 원칙: **증상을 고치지 말고 원인을 고친다.** 추측 수정을 반복하는 것이 가장 비싼 경로다.

## 절차 (순서를 지킨다)
1. **재현 먼저.** 실패를 다시 일으키는 최소 명령/입력을 확보한다. 재현 없이는 수정도 검증도 추측이다.
   - 가능하면 재현을 **실패하는 테스트**로 박제한다 — 이게 곧 완료 기준이 된다.
2. **증거 수집.** 스택트레이스는 아래(근원)부터 읽는다. 에러 메시지를 그대로 검색하기 전에
   이 레포 안에서 먼저 찾는다(`grep`) — 같은 실패의 처리 전례가 있을 수 있다.
3. **가설 → 이분탐색.** 의심 지점을 반으로 줄여간다: 입력 절반, 커밋 절반(`git bisect`),
   코드 경로 절반(조기 return/로그). 한 번에 하나의 변수만 바꾼다.
4. **근본 원인을 한 문장으로.** "X 가 Y 일 때 Z 가 None 이라 터진다"로 말할 수 없으면 아직 모르는 것이다.
5. **최소 수정 + 회귀 테스트.** 1의 실패 테스트가 통과로 바뀌는 것이 완료. 관련 없어 보이는
   코드 정리는 하지 않는다.

## 함정
- **에러를 삼키지 않는다**: `except: pass` 는 디버깅의 반대다. 잡을 예외를 특정하고 나머지는 올린다.
- **간헐 실패**는 순서·시간·공유 상태를 의심한다. 반복 실행(`pytest -x --count` 류)으로 빈도를 먼저 잰다.
- **환경 차이**(버전·PATH·환경변수)를 코드보다 먼저 의심할 것 — 어제까지 됐다면 코드가 아니라 환경이 바뀐 경우가 많다.
- 10분 이상 진전이 없으면 지금까지의 가설·반증을 정리해 보고하고 방향을 확인받는다.
