# 개발 (Development)

> 프로젝트 명령어와 절대 규칙은 `AGENT.md` 를 따른다. 이 문서는 **어떻게 일할지**만 다룬다.

## Read → Think → Plan → Edit → Verify
1. **Read** — 고치기 전에 인접 코드를 읽어 이 레포의 관례를 파악한다. 라이브러리는 매니페스트(import·패키지 파일)로 존재를 확인한다.
2. **Think** — 아래 §코드 짜기 전에 생각하기.
3. **Plan** — 3단계 이상이거나 모호하면 `PLAN.md` 에 단계를 적되, **단계마다 verify 줄을 함께** 적는다.
4. **Edit** — 최소 변경. 요청 범위 밖은 건드리지 않는다.
5. **Verify** — `.scripts/verify.sh` 통과 전에는 "완료"가 아니다.

## 코드 짜기 전에 생각하기
가장 싼 수정은 틀린 코드를 애초에 안 쓰는 것이다.

- 두 해석이 모두 그럴듯하면 묵묵히 고르지 말고 둘 다 적어 묻는다. **잘못된 무언의 선택 한 번이 질문 한 번보다 비싸다.**
- 같은 문제를 더 작게 푸는 길이 보이면 코드 짜기 전에 제안한다.
- 막히면 무엇이 헷갈리는지 이름 붙여 묻는다. 혼란을 추측 코드로 덮지 않는다.

```
나쁨:  "유저 데이터 export 기능 추가해줘" → 곧장 csv/json/xml exporter 작성
좋음:  "API 엔드포인트로, 페이지네이션 JSON, PII 제외라고 가정했습니다. 맞나요?"
```

## 목표 주도 실행
LLM 은 검증 가능한 목표를 향해서는 안정적으로 루프를 돈다. 모호한 명령형에는 표류한다.
작업을 **"X 한다 → Y 로 검증한다"** 형태로 다시 적는다.

| 받은 요청 | 다시 적은 목표 |
|---|---|
| "검증 로직 추가" | 잘못된 입력 테스트를 먼저 작성 → 통과시킨다 |
| "버그 수정" | 버그를 재현하는 테스트 작성 → 통과시킨다 |
| "X 리팩터링" | 기존 테스트가 변경 전·후 모두 통과 |
| "더 빠르게" | 목표치 있는 벤치마크 작성 → 달성 |

성공 기준이 약하면("작동하게 해줘") 매 단계 사람 확인이 필요하다. 강하면 혼자 끝까지 간다.

테스트를 먼저 쓸 때는 **실패하는 것을 반드시 눈으로 확인한다** — 실패를 본 적 없는
테스트는 기존 동작을 재확인하고 있거나 잘못된 것을 재고 있을 수 있다. 그다음
통과에 필요한 최소 코드만 쓴다.

## 증거 없이 완료를 주장하지 않는다
"통과할 것 같다"·"아마 됐을 것" 은 보고가 아니다. 주장하기 전에 **그 주장을 증명하는
명령을 이 자리에서 실행하고 출력을 확인**한다.

| 주장 | 증거 |
|---|---|
| "테스트 통과" | 방금 돌린 테스트 출력, 실패 0 |
| "버그 고침" | 원래 증상을 재현하던 테스트가 지금 통과 |
| "요구사항 충족" | 요구사항을 한 줄씩 대조한 체크리스트 |

(참고: [obra/superpowers](https://github.com/obra/superpowers) 의 test-driven-development ·
verification-before-completion 에서 발췌·압축.)

## 이 레포의 관례
- 범위 밖에서 발견한 표류·죽은 코드는 고치지 말고 `.docs/plans/tech-debt.md` 에 적고 넘어간다.
- 판단이 애매하면 `.docs/design/core-beliefs.md` 를 기준으로 결정한다.
- 주석은 **WHY 가 비자명할 때만** 한 줄. WHAT 은 이름이 설명한다.
- 외부에서 온 입력은 경계에서 검증·이스케이프한다(인젝션·경로 탈출·역직렬화).
- 타입체크와 테스트는 **코드** 정확성만 본다. 기능 정확성은 직접 확인해야 한다 —
  UI 변경은 dev 서버를 띄워 골든패스와 회귀를 눈으로 본다. 확인하지 못했으면 "성공"이라 하지 않고 그 사실을 말한다.
