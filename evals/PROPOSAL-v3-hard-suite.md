# 평가 스위트 v3 설계: 포화 해소와 카테고리 재편

> **상태: 구현 완료.** 스위트 v2(28태스크)를 폐기하고 16태스크로 교체했다.
> 현행 스펙은 [`README.md`](README.md), 이 문서는 설계 근거를 보존한다.

## 1. 왜 갈아엎는가: 스위트 v2는 포화됐다

2026-08-05 전량 실측(Opus, 56슬롯)에서 **28태스크 중 24개가 양 조건 무승부**,
그중 19개는 양쪽 다 1.00이었다. 평균 0.94/0.94. 태스크가 프론티어 모델의 능력
아래에 있으면 A/B는 아무것도 구분하지 못한다 — 천장에서는 Δ가 나올 공간이 없다.

문헌 둘이 같은 문제와 처방을 제시한다.

- **[Harness-Bench](https://arxiv.org/abs/2605.27922)** (8카테고리·106태스크):
  하네스 간 23.8%p 격차를 만든 것은 고립된 도구 호출이 아니라 **종단 워크플로**다.
  실패의 대부분이 계약/형식 위반(36.4%)·도구 복구 실패(24.6%)·근거 부족(14.6%)·
  산출물 미제출(11.1%)·상태 연속성(9.3%)에서 나온다 — 우리 v2 태스크는 이 실패
  모드들을 거의 유발하지 못한다.
- **[Don't Blame the LLM](https://arxiv.org/abs/2607.03691)** (하네스 35릴리스 종단 연구):
  SWE-bench Verified를 소요 시간으로 계층화(easy <15분 / medium ~1시간 / hard 1~4시간)해
  샘플링했고, 실패 실행이 성공 대비 2.7배 자원을 쓴다는 것 — 효율을 점수 밖에 두면
  하네스 회귀를 놓친다는 것 — 을 보였다.

## 2. 설계 원칙 5가지 (실패 모드를 겨냥한다)

함정 지식이 아니라 **실행 품질**이 갈리게 만든다. 각 원칙은 Harness-Bench 실패
분류의 상위 항목 하나씩을 겨냥한다.

| 원칙 | 겨냥하는 실패 모드 | 구현 |
|---|---|---|
| ① 엄격한 산출물 계약 | 계약/형식 위반 36.4% | 스키마 고정 deliverable(JSON·CSV·형식 문서), 필드·값 완전 일치 오라클 |
| ② 계층 숨은 결함 | 도구 복구 실패 24.6% | 보이는 결함을 고치면 다음 결함이 드러남 — 검증 루프를 안 돌면 중간에서 멈춤 |
| ③ 근거 강제 | 근거 부족 14.6% | 판정에 file:line·SHA 증거를 요구하고 증거 실재를 채점기가 대조 |
| ④ 상태 연속성 | 상태/연속성 9.3% | 세션 분할(`prompts:`) + 체크포인트 재개, exactly-once 오라클 |
| ⑤ 멱등·가역성 | (SRE 고유) | 채점기가 스크립트를 두 번 실행·롤백해 데이터 보존을 검사 |

난이도는 Don't Blame 방식으로 계층화해 `task.yaml`에 선언한다:
`difficulty: medium`(~1시간 상당) / `hard`(1시간+ 상당). easy는 두지 않는다 —
포화 확인이 목적이 아니라 변별이 목적이다. 대조군은 06(`control: true`,
`mechanism: none` — 순수 데이터 추출이라 하네스가 이기면 벤치마크가 기운 것)이다.

## 3. 카테고리: Harness-Bench 8종 × 2태스크 = 16개

Harness-Bench의 8개 워크플로 카테고리를 로컬 샌드박스(네트워크 차단) 제약에 맞게
번안했다. 태스크 상세는 각 `tasks/<id>/README.md`.

| 카테고리 | 태스크 | 원칙 | 기제 |
|---|---|---|---|
| swe-maintenance | 01 계층 회귀 수정 · 02 API 마이그레이션 | ②① | verify-gate |
| data-analytics | 03 더러운 장부 집계 · 04 이중 장부 대사 | ①② | skill-text |
| workspace-ops | 05 자산 재구성(멱등 스크립트) · 06 로그 포렌식(대조군) | ⑤① | guard-bash · none |
| knowledge-evidence | 07 주장 감사(증거 대조) · 08 이력 포렌식(SHA 증거) | ③ | skill-text |
| office-comm | 09 릴리스 노트 · 10 사후 보고서(수치 대조) | ①③ | doc-writing |
| vertical-workflow | 11 티켓 라우팅 엔진 · 12 라이선스 게이트 | ①② | skill-text |
| long-autonomy | 13 3세션 단계 리팩터링 · 14 체크포인트 배치 재개 | ④② | session-context |
| sre-devops | 15 멱등 DB 마이그레이션 · 16 릴리스 위생 | ⑤①③ | verify-gate·scaffold |

v2에서 유지하는 것: A/B 방법론, held-out 채점, `Safety × Completion × Process` 공식
(Harness-Bench의 Security × Completion × Process 번안 — v2 P4에서 이미 도입),
세션 분할 러너, 컴포넌트 절제, 기제 선언, golden/baseline/parity 자기검증.

v2에서 버리는 것: 태스크 28개 전부. 함정 지식형(02 시크릿, 08 셸인젝션 등)은
프론티어가 하네스 없이 다 피했고, 일상형(21-25)은 비용 축에서만 신호가 났다 —
비용은 v3에서도 계속 기록한다(효율은 Process 축에 이미 반영).

## 4. 스키마 변경

- `task.yaml`에 `difficulty: medium | hard` 추가 (Don't Blame 계층화).
- `category`는 위 8종 고정 어휘로 재정의.
- 스코어카드에 카테고리별·난이도별 집계 표 추가 — "어려운 태스크에서만 갈리는가"를
  표 하나로 읽게 한다.

## 5. 한계

- **포화 해소 가설은 실측에서 기각됐다(2026-08-06).** Opus 32슬롯에서 **완료(Completion)가
  32/32 만점**이고 조건 간 판정이 갈린 채점 항목이 **0개**였다. 계약 엄격화·계층 결함·
  근거 대조·상태 연속성 어느 것도 프론티어의 천장을 낮추지 못했다. 남은 점수 차(-0.01)는
  전부 Process 축의 토큰 효율 감점이다. 다음 수단은 난이도 강화가 아니라 측정 축의 변경으로
  보인다 — 상세는 [`results/FINDINGS.md`](results/FINDINGS.md) 스위트 v3 절.
- 태스크당 소요가 커져 실측 비용도 커진다(v2 대비 태스크 수는 절반이지만
  태스크당 시간은 수 배). N=1 실측 기준 예상 비용은 v2 전량과 비슷한 수준.
- office-comm 계열의 결정론 채점은 형식·수치·포함/배제만 본다. 문장 품질은 재지
  않는다 — LLM 채점을 넣지 않는 대가로 받아들인다.
