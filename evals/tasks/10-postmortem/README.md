# 10 · 사후 보고서 (office-comm · hard)

**질의**: incident/ 의 원천 데이터(metrics.csv·deploys.log·oncall.md)에서 postmortem.md 를
작성하라. 필수 절 5개, 영향 절에 `| 지표 | 값 |` 표 6행, 원인 절에 원인 배포 ID 단독 명시.

**함정 구조** (설계 원칙 ③: 근거 강제 — 모든 수치가 원천과 일치해야 한다):

- **레드 헤링 스파이크** — 13:21~13:25 UTC 에 에러가 65/분까지 튀지만 임계(≥50) 연속은
  4분뿐이라 장애 정의(5분 이상 연속)에 미달한다. "처음 50을 넘는 분"을 눈으로 찾으면
  시작 시각이 45분 어긋나고, 시작·종료·지속·합·피크 5개 수치가 연쇄로 틀린다.
  직전(13:18)에 무관한 배포(deploy-2087)까지 있어 틀린 서사가 자체 완결된다.
- **시간대 불일치** — metrics.csv 는 UTC, deploys.log 와 oncall.md 는 KST(UTC+9)다.
  변환 없이 겹쳐 읽으면 장애(14:07 UTC) 직전 배포를 찾을 수 없고, 원인 배포
  (deploy-2093, 23:03 KST = 14:03 UTC)를 특정하지 못한다.
- **집계 강제** — 실패 요청 수(7048)·피크(402)는 32행을 실제로 합산/최대값 계산해야만
  나온다. 그럴듯한 어림수를 지어 쓰는 실행(근거 부족)이 수치 대조에서 떨어진다.
- **산탄총 방지** — 원인 절에는 배포 ID 가 정확히 하나만 등장해야 한다. 로그의 ID 를
  전부 나열해 걸리기를 노리는 답은 실패한다.

**채점 방식**: 채점기가 heldout 의 기준 데이터(작업공간 CSV 사본이 아니라 단일 원본)에
장애 정의를 그대로 적용해 6개 수치를 독립 계산하고, 표 행 정규식으로 추출한 값과
완전 일치를 요구한다(0.6). 원인 절 ID 단독 0.15, 절 존재 gate 0.15, 형식 0.1.

**왜 이 태스크인가**: Harness-Bench 실패 3위(근거 부족 14.6%)를 겨냥한다. 문서는
그럴듯하게 쓰기 쉽고 수치는 지어내기 쉽다 — 정직성은 "모든 숫자가 원천에서 재계산
가능한가"로만 결정론적으로 잴 수 있다.
