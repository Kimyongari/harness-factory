# 14 · 체크포인트 배치 재개 (long-autonomy · hard)

**질의**: process_spec.md 계약대로 배치 프로세서 process.py 를 작성하라. 세션 1은
rec_001~rec_150 까지만, 세션 2(대화 기억 없음)는 "나머지 전부, 재처리 금지" 만 받는다.

**함정 구조** (설계 원칙 ④ 상태 연속성 + ② 계층 결함):

- **exactly-once 가 계약** — 자연스러운 구현(inbox 전체를 돌며 append)은 세션 2 재실행에서
  rec_001~150 을 통째로 중복 기록한다. 산출물(journal/errors)을 체크포인트로 읽어
  건너뛰는 재개 로직이 있어야 완주한다. 세션 2 프롬프트는 상태를 알려주지 않는다 —
  어디까지 처리됐는지는 작업공간 파일에만 남아 있다.
- **포이즌 12건** — 잘린 JSON(5)·꼬리 쓰레기(2)·필수 필드 결손(5). 유효 경로만 만들면
  세션 1 이 rec_007 에서 죽고, 죽은 지점까지의 부분 기록 위에서 재개까지 해야 한다.
  포이즌도 id 당 정확히 한 번만 errors.tsv 에 남아야 한다(체크포인트가 journal 만
  덮으면 재실행 때 에러가 중복 적재된다).
- **체크섬 정규화** — 파일마다 키 순서·들여쓰기가 다르게 저장돼 있다. 원문 바이트를
  해시하는 가장 짧은 구현은 전 항목에서 틀리고, spec 의 정규화 규칙
  (sort_keys·separators·UTF-8)을 그대로 따라야 맞는다.

**채점 방식**: 기대값(유효 288건의 체크섬, 포이즌 12건)은 작업공간이 아니라 held-out
사본 생성기에서 독립 재계산한다. 멱등성은 채점기가 완료 상태의 작업공간에서
process.py 를 실제로 한 번 더 실행해 산출물 불변을 확인한다. inbox 는 읽기 전용
계약이라 수정·소실은 fatal.

**왜 이 태스크인가**: Harness-Bench 실패 모드 "상태/연속성"(9.3%)의 재개 시나리오를
결정론 오라클(exactly-once)로 잰다. 세션 간 대화 기억이 없으므로, 하네스의
SessionStart 재주입·상태 기록 규율이 있는 조건과 바닐라 조건이 "중복 없이 이어받기"
에서 갈린다.
