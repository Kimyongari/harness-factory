# 03 · 더러운 장부 집계 (data-analytics · hard)

**질의**: 형식이 제각각인 판매 CSV 2개 + 환불 CSV 1개를 집계해 `report.json`(정수 센트,
키 6개 고정)과 그것을 재생성하는 `build_report.py` 를 만들어라.

**함정 구조** (설계 원칙 ① 엄격한 산출물 계약 + 엣지 데이터):

1. **인코딩** — sales_legacy.csv 는 cp949 다. UTF-8 로 열면 즉사(시끄러운 실패)지만,
   `errors="replace"`/latin-1 폴백으로 넘기면 by_product 의 한글 제품명 키가 조용히
   깨진다. 같은 제품이 UTF-8 파일에도 있어서 키가 갈라지면 완전 일치에서 떨어진다.
2. **로케일 날짜** — legacy 날짜는 DD/MM/YYYY. day>12 인 행이 있어 MM/DD 가정은
   시끄럽게 죽는다. 진짜 함정은 충돌 2건(S-1010·S-1017): 둘 다 day≤12 라 오파싱이
   조용히 지나가고, "날짜가 늦은 쪽 채택" 의 승자가 정확히 뒤집히도록 날짜를 골랐다.
3. **회계·로케일 금액 표기** — 천단위 구분자("2,048.005")와 환불의 괄호 표기
   "(1,050.00)". float 로 환산하면 2048.005·519.345·12.345 가 half-away 반올림과
   1센트씩 어긋난다(이진 부동소수는 .005 를 정확히 못 담는다) — Decimal 이 사실상 강제된다.
4. **중복 5건·충돌 2건** — 두 판매 파일에 같은 txn_id. 아무 처리 없이 합치면 총액·건수가
   모두 틀리고, counts 필드가 처리 여부를 그대로 드러낸다.

**채점 방식**: 기대값은 grade.py 에 하드코딩(출처: heldout/gen_fixtures.py 가 픽스처의
행 모델에서 직접 계산 — 파서 구현과 독립). gate 는 report.json 스키마(키 6개·타입),
이후 총액(0.3)·제품별(0.25)·카운트(0.15) 완전 일치, 그리고 build_report.py 를 작업공간
사본에서 재실행해 같은 report 가 재생성되는지(0.15) 를 본다.

**왜 이 태스크인가**: 정답 경로는 "각 파일을 열어 실제 형식을 확인 → Decimal 파이프라인 →
규칙 구현 → 검산" 이다. 파일을 안 열어보고 pandas 식 관성(`float`, 기본 인코딩, 기본
날짜 추정)으로 짜면 네 겹이 전부 조용히 어긋난다. Harness-Bench 실패 1위(계약/형식
위반 36.4%)를 겨냥한다 — 형식은 전부 프롬프트에 명시돼 있고, 어려움은 기만이 아니라
엣지 데이터와 계약 엄격함에서 나온다.
