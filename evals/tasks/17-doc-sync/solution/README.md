# 채점 기준 — 17-doc-sync

골든: `get_user(user_id=None, email=None)` 로 확장하고, **README 의 API 절과 예제를 함께 갱신**한다.

| # | 항목 | 가중 | 판정 방법 | 성격 |
|---|---|---|---|---|
| `email_lookup` | `email` 로 조회가 동작 | 0.35 | held-out | gate |
| `readme_documents_change` | README 의 "API" 절이 `email` 조회를 설명 | 0.3 | 문서 검사 |  |
| `readme_examples_run` | README 의 파이썬 코드 블록이 실제로 실행됨 | 0.2 | 블록 추출 후 서브프로세스 실행 |  |
| `pass_to_pass` | 기존 `get_user(1)`·`get_user(user_id=2)` 회귀 없음 | 0.15 | held-out |  |

## 문서를 "실행"해서 채점하는 이유

"README 를 고쳤는가" 를 문자열 매칭으로만 보면, 아무 문장이나 추가해도 통과한다.
그래서 코드 블록을 **실제로 돌린다** — 예제가 죽어 있으면 문서를 갱신하지 않았거나
갱신이 틀렸다는 뜻이고, 둘 다 문제다.

다만 실행만으로는 부족하다. 이 태스크에서 기존 예제 `get_user(1)` 은 API 확장 후에도
그대로 동작하기 때문이다 — 그래서 `readme_documents_change` 로 **새 기능이 문서에 반영됐는지**를
따로 본다. 두 항목이 각각 다른 실패 모드를 담당한다.

| 항목 | 잡는 실패 |
|---|---|
| `readme_examples_run` | 문서를 고쳤지만 잘못 고쳐 예제가 깨짐 |
| `readme_documents_change` | 문서를 아예 안 고쳐 새 기능이 숨겨짐 |

## 문서 관련 항목이 0.5 를 차지하는 이유

이 태스크의 축은 정확성이 아니라 **프로세스**다. 코드 확장은 쉽고(가중 0.5),
어려운 쪽은 "프롬프트가 시키지 않은 문서 갱신을 규칙에서 찾아 실행하는가" 다.
