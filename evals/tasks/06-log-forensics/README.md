# 06 · 로그 포렌식 (workspace-ops · medium)

**질의**: UTC 로 명시된 15분 장애 윈도우(02:10:00 이상 ~ 02:25:00 미만)에 대해 형식이
다른 로그 3종(app ERROR · gateway 5xx · worker PANIC)에서 이벤트를 모아, 계약이 고정된
timeline.csv(UTC ISO8601 · 정렬 · 타이브레이크)를 작성하라.

**함정 구조** (설계 원칙 ① 엄격한 산출물 계약):

- **시간대 정규화** — app.jsonl 의 ts 는 **KST(+09:00)**, gateway.log 는 UTC,
  worker.log 는 epoch 초. 오프셋을 무시하고 naive 하게 읽으면
  `2026-03-14T02:13:05+09:00` 같은 레드 헤링 2건(실제 UTC 는 전날 17시)이 윈도우 안으로
  들어오고, 진짜 이벤트 6건(KST 11:1x~11:2x)이 전부 빠진다 — 재현율과 정밀도가 동시에
  무너진다.
- **경계 엄격성** — gateway 에 02:09:59(시작 1초 전)와 02:25:00 정각(미만이므로 제외)의
  5xx 를 심었다. 윈도우 밖 worker PANIC 2건 포함 레드 헤링 총 6건.
- **수집 기준 필터** — 윈도우 안에도 app WARN/INFO, gateway 200/404, worker ERROR
  (PANIC 아님) 줄이 있다. "윈도우 안 = 전부"로 긁으면 정밀도가 떨어진다.
- **정렬 타이브레이크** — 02:12:41 에 app 과 gateway 이벤트가 동시에 있다.
  같은 시각은 source 알파벳순(app < gateway)이 계약이다.

**채점 방식**: 기대 타임라인 18행은 held-out 에 하드코딩(생성 스크립트도 held-out).
gate = 파일 존재 + 헤더. 행 집합은 재현율(기대행 전부 존재)과 정밀도(잉여·중복 없음)를
분리해 배점하고, 시각 형식(`...Z` 초 단위)과 정렬은 별도 항목.

**왜 이 태스크인가**: 파싱 자체는 쉽다. 갈리는 것은 계약 준수 — 시간대를 UTC 로
정규화했는가, 경계·타이브레이크·형식을 계약대로 지켰는가다. Harness-Bench 실패 1위
(계약/형식 위반 36.4%)를 medium 난이도에서 재는 대조군 역할.
