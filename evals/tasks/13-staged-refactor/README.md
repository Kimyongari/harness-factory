# 13 · 3세션 단계 리팩터링 (long-autonomy · hard)

**질의**: REFACTOR_PLAN.md 의 3단계 리팩터링(파서 분리 → 포매터 분리 → 재수출 셔틀 축소)을
세 세션에 걸쳐 수행하라. 세션 1만 구체적 지시를 받고, 세션 2·3 프롬프트는
"이어서 진행해줘 / 마무리해줘" 뿐이다.

**함정 구조** (설계 원칙 ④ 상태 연속성 + ② 계층 결함):

- **상태가 컨텍스트 밖에 있다** — 세션 2·3은 대화 기억이 없다. 어느 단계까지 왔는지,
  다음에 뭘 해야 하는지는 REFACTOR_PLAN.md 의 체크박스·진행 기록과 코드 상태에만
  남는다. 세션 1이 기록을 안 남기면 세션 2는 계획 파일을 처음부터 다시 읽고 맥락을
  재구성해야 하고, 그마저 없으면 중간에서 멈춘다.
- **숨은 인터페이스 의존** — 포맷 함수들이 파싱 계층의 내부 헬퍼(`_normalize_unit`)와
  내부 테이블(`_UNIT_SYMBOLS`)을 직접 쓴다. 단계 2에서 기계적으로 잘라 옮기면
  모듈 경계 규칙("공개 이름만 사용")을 어긴다 — 파서 기능의 공개 승격이라는
  인터페이스 재설계가 필요하다.
- **행동 보존이 계약** — 반환 dict 키, 예외 메시지의 line 번호, 반올림·표 정렬 규칙까지
  현재 동작과 동일해야 한다. held-out 테스트가 새 모듈을 직접 import 해 대조한다.
  (파이썬 내장 `parser` 모듈과의 충돌을 피해 모듈명은 measure_parser/measure_format 으로
  계획서에 고정했다.)

**채점 방식**: 세션을 몇 번에 끝냈는지는 재지 않는다(러너가 세션을 쪼갠다). 최종
산출물의 성질만 본다 — 새 모듈 2개의 행동 보존(gate), 재수출 셔틀·공개 경계,
measurelib 경유 레거시 동작(held-out 사본으로 판정), 계획 문서의 체크·진행 기록.

**왜 이 태스크인가**: Harness-Bench 실패 모드 "상태/연속성"(9.3%)을 겨냥한다.
"이어서" 만 받은 세션이 완주하려면 상태가 파일에 남아 있어야 한다 — 하네스의
SessionStart 재주입(session-context.sh)과 PLAN 기록 규율이 값을 하는지 잰다.
