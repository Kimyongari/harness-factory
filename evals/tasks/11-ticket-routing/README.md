# 11 · 티켓 라우팅 엔진 (vertical-workflow · hard)

**질의**: POLICY.md 12조를 `route(ticket) -> str` 로 구현하라. 보이는 테스트(5개)는
단일 규칙 케이스뿐이다.

**함정 구조** (설계 원칙 ①② — 계약 엄격함·엣지 데이터, 기만 없음):

1. **예외의 예외의 예외** — VIP 는 vip 큐(제6조), 단 billing 이면 finance-priority(제7조),
   단 urgent 면 escalation(제8조)이 전부를 이긴다. 보이는 테스트는 이 교차를 하나도
   건드리지 않는다. held-out 이 3중 교차 12케이스를 찌른다.
2. **UTC→KST 변환 함정** — 영업시간 판정은 KST 기준인데 티켓 시각은 UTC 로 들어온다.
   금요일 UTC 09:00 = KST 18:00 정각(영업시간 외), UTC 15:00 = KST 토요일 자정(주말),
   일요일 UTC 23:59 = 월요일 KST 08:59(아직 영업 전). 변환을 빼먹거나 18:00 포함/미포함을
   뒤집으면 time 그룹 12케이스가 떨어진다.
3. **우선순위 사다리의 중간 칸** — 영업시간(제5조)은 언어(제4조)·첨부(제3조)를 이기지만
   VIP(제6·7조)에는 진다. "VIP 는 주말에도 vip 큐", "ja 티켓도 주말엔 next-business-day"
   같은 중간 칸 교차가 misc·time 그룹에 있다. 그 외 `zh-TW`→zh, 첨부 합계 경계
   (10,485,760 초과만), 누락 필드 기본값.

**왜 이 태스크인가**: 정책 문서는 명확하고 우선순위 요약표(제12조)까지 있다. 어려움은
문서를 끝까지 정확히 읽고 조항 상호작용을 코드로 옮기는 데서 나온다. 쉬운 테스트 통과
지점에서 멈추는 실행(0.15)과 40개 교차 케이스를 전부 견디는 실행(1.00)이 갈린다.

**채점**: gate 0.15(단일 규칙) + precedence 0.25 + time(KST) 0.25 + misc 0.20 +
시그니처·입력 불변 0.15. 기대값은 골든 구현으로 산출해 `solution/heldout/cases.json` 에
하드코딩(재생성: `gen_cases.py`).
